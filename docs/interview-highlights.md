# 면접에서 보여줄 것

당연하게 여겨서 말하지 않고 넘어가기 쉬운 강점을 코드, git 이력, 정책 문서에서 뽑아 정리했다.
기준일은 2026-11-15다. 모든 항목에 근거(파일이나 커밋)를 붙였으니, 면접 전에 그 파일을 한 번씩 열어 본다.

- 예상 질문과 Next.js·TypeScript 지식은 [interview-prep.md](./interview-prep.md)에 있다.
- 이 문서는 "무엇을 꺼내 보여줄지"와 "어떤 문장으로 말할지"만 다룬다.

## 0. 한눈에 보기

기능 목록(로그인, 장바구니, 결제, 관리자)은 README에 이미 있고, 다른 지원자의 쇼핑몰과 구별되지 않는다.
이 프로젝트가 구별되는 지점은 세 가지다.

1. **돈과 재고가 걸린 흐름을 실패하는 경우까지 설계했다.** 결제 승인, 환불, 배송 완료가 중간에 깨져도 돈과 주문이 어긋나지 않게 순서를 잡았다.
2. **취약점을 스스로 찾아 고치고, 다시 생기지 않게 규칙으로 남겼다.** 고친 기록이 커밋 메시지에 원인과 검증 방법까지 남아 있다.
3. **혼자 하는 프로젝트를 운영 중인 서비스처럼 굴린다.** 환경 분리, 배포 규칙, 장애 대응 절차, 결정 기록이 있다.

### 30초 소개

> 되팔이를 줄이려고 한 사람이 같은 상품을 5개까지만 보유할 수 있게 한 쇼핑몰입니다.
> 기획, 디자인, 프론트, 백엔드, 배포를 혼자 했습니다.
> 가장 신경 쓴 곳은 결제입니다. 클라이언트가 보낸 금액을 믿지 않고 서버가 다시 계산하고,
> 결제 승인 뒤에 주문 저장이 실패하면 결제를 자동으로 취소합니다.
> 만들고 끝낸 게 아니라 보안 점검, 성능 측정, 구조 개편을 거치며 1년 넘게 고쳐 왔습니다.

## 1. 문제를 정의하고 규칙을 설계했다

### 1-1. "5개 한도"는 단순한 숫자 제한이 아니다

- **한 일**: 한도를 "지금까지 산 개수"가 아니라 "지금 보유 중인 개수"로 정의했다. 장바구니 수량과 배송 중 수량(`user.keep`)을 더해서 센다. 결제하면 `keep`에 더하고, 배송 완료나 환불이 되면 `keep`에서 뺀다.
- **눈여겨볼 점**: 요구사항을 데이터 모델과 상태 변화로 옮긴 것이다. "배송이 끝나면 다시 살 수 있다"는 규칙 하나 때문에 결제, 배송 완료, 환불 세 곳이 모두 `keep`을 건드려야 한다. 이 세 곳이 같은 순수 함수(`mergeKeep`, `subtractKeep`)를 쓴다.
- **증거**: `src/features/purchase/lib/orderPolicy.ts`, `orderPolicy.test.ts`, README "구매 정책"
- **말할 문장**: "한도를 누적 구매가 아니라 보유 수량으로 정의했고, 그래서 결제·배송 완료·환불이 같은 계산 함수로 보유 수량을 조정합니다."

### 1-2. 한도를 우회하는 방법까지 생각했다

- **한 일**: 계정을 여러 개 만들면 5개 한도를 피할 수 있다. 그래서 페이지 응답에 기기 ID 쿠키를 심고, 결제할 때 기기 ID, IP, 배송지를 주문에 저장한다. 관리자 주문 화면에서 "같은 상품을 산 다른 계정 중 기기·IP·배송지가 겹치는 주문"을 표시한다.
- **눈여겨볼 점**: **막지 않고 표시만 한다.** 가족이 기기나 주소를 같이 쓰는 경우가 있어서 자동 차단은 오탐이 난다고 판단했다. 쿠키는 사용자가 바꿀 수 있으므로 `httpOnly`로 두고 UUID 형식만 받는다. IP 헤더는 Vercel 밖으로 옮기면 다시 확인해야 한다는 주석까지 남겼다.
- **증거**: `src/features/order-manage/lib/findSuspects.ts`와 테스트, `src/shared/lib/clientSignals.ts`, `src/proxy.ts` 아래쪽 쿠키 설정
- **말할 문장**: "핵심 규칙의 빈틈을 제가 먼저 찾았고, 자동 차단 대신 관리자에게 신호를 보여 주는 쪽을 골랐습니다. 오탐으로 정상 고객을 막는 비용이 더 크다고 봤습니다."

### 1-3. 장바구니를 일부러 두 층으로 나눴다

- **한 일**: 상품 상세에서 수량을 고르는 동안은 브라우저 메모리(Jotai)에만 두고, "장바구니 담기"를 눌러야 DB에 저장한다.
- **눈여겨볼 점**: 중복처럼 보이지만 의도한 설계다. 수량을 올렸다 내렸다 할 때마다 서버에 쓰지 않고, 실수로 담기는 일도 없다. 5개 한도는 두 층을 합쳐서 계산한다.
- **증거**: `src/features/cart/model/useTempCart.ts`, `useCart.ts`, CLAUDE.md "데이터 레이어" 마지막 항목
- **말할 문장**: "탐색 중인 수량과 확정된 장바구니를 나눠서, 서버 쓰기를 줄이고 한도 계산은 둘을 합쳐서 합니다."

### 1-4. 살 수 없게 된 상품은 장바구니에서 알아서 빠진다

- **한 일**: 장바구니를 조회할 때 재고와 비교해서 품절이나 재고 초과 상품을 장바구니에서 지운다. 결제 직전에도 한 번 더 확인한다. 장바구니, 배송 중 수량, 상품 정보는 MongoDB `$facet`으로 한 번에 가져온다.
- **증거**: `src/app/api/getCart/route.ts`, `src/features/purchase/lib/validateStock.ts`
- **말할 문장**: "결제 단계에서 처음 실패를 보여 주지 않으려고, 장바구니를 열 때 살 수 없는 상품을 먼저 정리합니다."

## 2. 돈이 걸린 흐름을 실패까지 설계했다

### 2-1. 결제 승인: 돈이 빠지기 전에 거절하고, 빠진 뒤에는 되돌린다

- **한 일**: 순서가 핵심이다.
  1. 재고 확인
  2. 금액·포인트·한도를 DB 기준으로 다시 계산 (`verifyOrder`)
  3. Toss 승인 호출. 여기서 실제로 돈이 빠진다
  4. 포인트 차감, 재고 차감, 주문 생성, 장바구니 비우기를 하나의 트랜잭션으로
  5. 트랜잭션이 실패하면 Toss 결제 취소
  6. 취소마저 실패하면 관리자가 처리할 수 있게 오류 컬렉션에 기록
- **눈여겨볼 점**: 거절할 수 있는 것은 모두 3번 앞에 뒀다. 외부 호출(Toss)은 DB 트랜잭션으로 되돌릴 수 없어서 트랜잭션 밖에 두고, 대신 취소로 보상한다. 트랜잭션 안의 각 단계는 실패하면 반드시 throw한다. 조용히 `{ ok: false }`를 돌려주면 일부만 처리된 주문이 커밋되기 때문이다.
- **증거**: `src/app/api/postPaymentsConfirm/route.ts`, 커밋 `72888de`
- **말할 문장**: "외부 결제와 DB를 하나의 트랜잭션으로 묶을 수 없어서, 검증을 승인 앞에 몰고 승인 뒤 실패는 결제 취소로 보상합니다. 보상도 실패하는 경우까지 기록으로 남깁니다."

### 2-2. 클라이언트가 보낸 값은 금액 말고도 믿지 않는다

- **한 일**: 결제 금액, 사용 포인트, 적립 포인트, 상품 이름까지 서버가 DB에서 다시 읽어 계산한다. 주문에 저장하는 상품 목록도 클라이언트 값이 아니라 검증된 값으로 새로 만든다. 배송 완료와 환불은 요청 본문이 아니라 주문 문서에서 이메일, 상품 목록, 포인트를 읽는다.
- **눈여겨볼 점**: 금액·배송비·포인트 규칙을 순수 함수 파일 하나에 모았다. 화면과 서버가 같은 파일을 쓰게 해서, 배송비를 바꿨을 때 화면 금액과 서버 검증이 어긋나 결제가 전부 거절되는 일을 막는다.
- **증거**: `src/features/purchase/lib/verifyOrder.ts`, `orderPolicy.ts`, `docs/policies/engineering.md` "금액 계산식 단일 출처"
- **말할 문장**: "브라우저에서 온 숫자는 표시용일 뿐이고, 돈에 관한 값은 전부 서버가 다시 계산합니다."

### 2-3. 한도를 세 번 검사하고, 각 검사의 역할이 다르다

| 위치 | 역할 | 경쟁 조건 |
|---|---|---|
| 클라이언트 hook | 즉시 알려 주는 UX | 막지 못함 |
| 장바구니 API (`checkCartLimit`) | 잘못된 요청을 일찍 거절 | 막지 못함 (주석으로 명시) |
| 결제 트랜잭션 (`reducePoint`, `reduceStock`) | 최종 방어 | 막음 |

- **눈여겨볼 점**: 세 번째만 원자적이다. `reducePoint`는 트랜잭션 안에서 사용자 문서를 읽고 쓰기 때문에, 탭 두 개에서 동시에 결제해도 한쪽이 쓰기 충돌로 다시 실행된다. `reduceStock`은 "재고가 주문 수량 이상일 때만 차감"을 조건부 업데이트 한 번으로 처리하고, 조건에 맞은 개수가 모자라면 전체를 되돌린다. 앞의 두 검사가 경쟁을 못 막는다는 사실을 알고 코드에 적어 뒀다.
- **증거**: `src/features/purchase/lib/reducePoint.ts`, `reduceStock.ts`, `checkCartLimit.ts` 위쪽 주석
- **말할 문장**: "앞의 두 검사는 사용자 경험과 빠른 거절을 위한 것이고, 동시 요청은 트랜잭션 안의 마지막 검사가 막습니다."

### 2-4. 버튼을 두 번 눌러도 한 번만 처리된다

- **한 일**: 주문 상태를 바꾸는 업데이트에 현재 상태를 조건으로 건다. "배송중인 주문만 배송 완료로" 바꾸므로 두 번째 요청은 아무 문서도 찾지 못한다. 그래서 적립 포인트가 두 번 지급되지 않는다. 리뷰 작성도 같은 방식으로 중복을 막는다.
- **증거**: `src/app/api/postSendingToFinish/route.ts`, `postCheckToSending/route.ts`, `protected/postReview/route.ts`
- **말할 문장**: "별도 잠금 없이, 업데이트 조건에 현재 상태를 넣어서 재시도와 더블클릭이 아무 일도 하지 않게 했습니다."

### 2-5. 환불은 돈부터 돌려준다

- **한 일**: 환불은 Toss 결제 취소를 먼저 하고, 성공하면 주문 상태·재고·보유 수량·사용 포인트를 트랜잭션으로 되돌린다. 결제 취소는 됐는데 DB 정리가 실패하면 오류 컬렉션에 기록하고 관리자 화면에 알린다.
- **눈여겨볼 점**: 순서를 반대로 하면 "주문은 환불 처리됐는데 돈은 안 돌아간" 상태가 생긴다. 고객에게 더 나쁜 쪽을 피하는 순서를 골랐다. 어긋났을 때 사람이 어떻게 복구하는지도 문서에 있다.
- **증거**: `postCheckToSending/route.ts`의 `refundOrder`, `docs/policies/incident.md` "결제 불일치 처리"
- **말할 문장**: "두 시스템이 어긋날 수밖에 없다면 고객에게 덜 나쁜 쪽으로 어긋나게 순서를 정했습니다."

### 2-6. 트랜잭션을 쓰지 않기로 한 곳도 이유가 있다

- **한 일**: 상품 등록은 트랜잭션으로 감싸지 않았다. 이미지 업로드는 외부 호출이라 되돌릴 수 없고, 상품 번호 카운터는 저장이 실패해 번호가 하나 비어도 문제가 없기 때문이다.
- **증거**: `src/app/api/postProduct/route.ts` 위쪽 주석
- **말할 문장**: "트랜잭션은 필요한 곳에만 씁니다. 되돌릴 수 없는 외부 호출이나 비어도 되는 값은 묶지 않았습니다."

## 3. 보안 문제를 스스로 찾아 고쳤다

커밋 메시지에 원인과 검증 방법이 남아 있어서 면접에서 화면으로 보여 주기 좋다.

### 3-1. 인증이 통째로 꺼져 있던 버그를 직접 찾았다

- **한 일**: 미들웨어에서 `/api`로 시작하는 경로를 일찍 통과시키는 코드가 `/api/protected` 로그인 검사보다 앞에 있었다. 그래서 로그인 검사 코드는 한 번도 실행되지 않았다. 순서를 바꾸고, 관리자 페이지와 관리자 API에 관리자 확인을 추가했다. 고친 뒤 `curl`로 401, 403, 리다이렉트를 하나씩 확인했다.
- **눈여겨볼 점**: "코드가 있다"와 "코드가 실행된다"는 다르다는 것을 직접 겪은 사례다. 같은 실수를 막으려고 "새 관리자 API는 목록과 matcher 양쪽에 등록한다"를 규칙으로 만들었다.
- **증거**: 커밋 `f0f52ef`, `src/proxy.ts`, `.claude/rules/api-routes.md`
- **말할 문장**: "인증 코드가 있어서 안전하다고 믿었는데, 실제로는 도달하지 못하는 코드였습니다. 그 뒤로는 보호 경로를 요청으로 직접 확인합니다."

### 3-2. 로그인만으로는 부족하다는 것을 알고 소유권을 검사한다

## 5. 구조를 바꾸고 줄였다

### 5-1. 큰 리팩터링을 작은 단계로 나눠서 했다

- **한 일**: Atomic Design 구조를 FSD(Feature-Sliced Design)로 옮겼다. shared, entities, features, widgets, views 순서로 5개 커밋에 나눴다. 인라인 스타일을 스타일 파일로 옮기는 작업도 8개 커밋으로 나눴다. 옮긴 뒤 레이어를 거꾸로 참조하는 곳을 찾아 정리했다.
- **눈여겨볼 점**: 한 번에 다 바꾸지 않아서 각 단계가 빌드되는 상태로 남았다. 아직 남은 위반(구매 기능이 장바구니 기능을 참조)을 "알고 있는 부채"로 문서에 적어 뒀다. 숨기지 않고 관리한다는 점이 어필이 된다.
- **증거**: 커밋 `4cacb0d`부터 `2a3d26a`, `6e5c8ce`, `8e85773`부터 `f1e8ca5`, `.claude/rules/fsd.md` "기존 예외"
- **말할 문장**: "구조 변경은 아래 레이어부터 한 단계씩 옮겼고, 아직 못 고친 의존은 목록으로 관리합니다."
- **준비할 답**: "혼자 하는데 FSD가 필요했나"는 반드시 나온다. 바꾸기 전에 무엇이 불편했는지 본인 경험으로 답을 준비한다.

### 5-2. 안 쓰는 것을 지웠다

- **한 일**: 설정만 있고 돌아가지 않던 Jest와 MSW를 지우고 Node 내장 테스트 러너로 바꿨다. 쓰지 않는 의존성(mongoose, swr 등), 호출되지 않는 API와 파일, 자체 방문 통계 수집 코드를 지웠다. 방문 통계는 GA4로 옮겼다.
- **눈여겨볼 점**: 지우는 것은 "이게 정말 안 쓰이는지" 확인해야 해서 추가하는 것보다 어렵다. 테스트 러너를 고를 때도 순수 로직만 테스트한다는 범위에 맞춰 의존성이 없는 쪽을 골랐다.
- **증거**: 커밋 `b8fe402`, `e753cf0`, `d674d00`
- **말할 문장**: "돌아가지 않는 테스트 설정을 두는 것보다, 실제로 도는 작은 테스트가 낫다고 판단했습니다."

### 5-3. App Router 기능을 목적에 맞게 썼다

| 기능 | 쓴 곳 | 이유 |
|---|---|---|
| Parallel Routes | 상품 상세의 정보·리뷰·문의 탭, 관리자 주문 상태 탭 | 탭마다 URL과 로딩 화면을 따로 가짐 |
| Intercepting Routes | 주문 내역의 리뷰 작성 모달 | 목록 위에 모달로 뜨고, 주소로 직접 들어오면 페이지로 열림 |
| `generateMetadata`, `sitemap`, `robots` | 상품 상세, 사이트 전체 | 검색 노출과 공유 미리보기 |
| `loading`, `error`, `not-found` | 탭, 상품 상세, 전체 | 구간별 로딩과 오류 화면 |

- **눈여겨볼 점**: 서버 컴포넌트에서 자기 API를 호출하면 세션 쿠키가 없어 401이 난다는 것을 겪고, 조회 로직을 공용 서버 함수로 빼서 API와 페이지가 같이 쓰게 했다.

### 5-4. 타입을 조였다

- `any`를 없애고, MongoDB 컬렉션에 문서 타입을 제네릭으로 줘서 조회 결과와 배열 수정 연산이 타입 검사를 받게 했다. (`src/shared/api/docs.ts`)

### 5-5. 지시어 하나를 지웠더니 빌드가 깨졌다

- **한 일**: 서버 컴포넌트인 `Header`에 잘못 붙어 있던 `'use server'`를 지웠더니 홈이 500을 냈다. 클라이언트 컴포넌트(`SiteFrame`)가 위젯 barrel(`widgets/index.ts`)을 import하고 있었고, 그 barrel이 `Header`를 내보내고 있어서 DB 모듈이 브라우저 번들에 끌려 들어갔다. 그동안은 잘못 붙은 `'use server'`가 우연히 이를 막고 있었다. `Header`를 barrel에서 빼고 layout이 직접 import하게 고쳤고, 규칙 문서에 적었다.
- **눈여겨볼 점**: 타입 검사, 린트, 테스트는 모두 통과했다. 페이지를 실제로 띄워 보고서야 드러났다. "서버 전용 코드가 클라이언트 번들에 들어가는 경로"를 설명할 수 있는 실제 사례다.
- **증거**: 커밋 `chore: 잘못 쓴 'use server'와 안 쓰는 파일 삭제`, `src/widgets/index.ts` 위쪽 주석, `.claude/rules/fsd.md`
- **말할 문장**: "barrel 파일 하나가 서버 코드와 클라이언트 코드를 같이 내보내면, 클라이언트가 그 파일을 import하는 순간 서버 코드까지 번들에 들어갑니다. 정적 검사로는 안 잡혀서 빌드와 화면 확인을 꼭 합니다."
