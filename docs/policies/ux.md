# 프론트 UX 정책 (비기능)

상태 표기와 문서 규칙은 [README](./README.md) 참고. 색·글꼴·컴포넌트 규격은 [design-system.md](../design-system.md), 아이콘·색 사용·접근성·문구 톤은 [design.md](./design.md)를 따른다.

## 로딩 표시 시점
- 상태: 확정
- 정책: 기다리는 시간에 따라 보여주는 것을 나눈다.
  - 클릭 즉시(0.1초 안): 누른 버튼이 바로 반응한다 (disabled + 문구 변경, 예: `결제하기` → `결제 중...`). 이건 지연 없이 항상 한다.
  - 0.3초 이상: 영역 로딩(스켈레톤이나 스피너)을 보여준다. 0.3초보다 빨리 끝나는 요청은 아무것도 띄우지 않아서 화면이 깜빡이지 않게 한다.
  - 10초 이상: "응답이 늦어지고 있습니다" 안내와 다시 시도 버튼을 보여준다. 결제 승인처럼 다시 보내면 안 되는 요청은 재시도 버튼 대신 주문 내역 확인 링크를 준다.
- 추천값 근거: 사용자는 약 1초부터 흐름이 끊겼다고 느낀다(Nielsen 응답 시간 기준 0.1초 / 1초 / 10초). 3초부터 로딩을 보여주면 그 전 2~3초 동안 화면이 멈춘 것처럼 보여서 다시 클릭하게 된다. 그래서 기준을 0.3초로 낮췄다.
- 이유: 지금은 상품 탭(info·review·qna)과 마이페이지(like·history)에만 `loading.tsx`가 있고, 내용은 `INFO LOADING...` 같은 텍스트다. 버튼 클릭 후 요청 중 상태는 대부분 표시되지 않는다.
- 코드: `src/app/(router)/[code]/@tab/*/loading.tsx`, `src/app/(router)/mypage/@menu/*/loading.tsx`
- 구현 시 바뀌는 곳: 0.3초 지연 표시용 훅 하나(`shared/hooks`), `loading.tsx`를 스켈레톤으로 교체
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 스켈레톤과 레이아웃 고정
- 상태: 확정
- 정책: 모양을 미리 아는 영역(상품 카드 목록, 리뷰 목록, 주문 내역)은 실제와 같은 크기의 스켈레톤을 쓰고, 모양을 모르는 짧은 작업은 스피너를 쓴다. 이미지와 비동기 영역은 높이를 미리 잡아서, 로딩이 끝날 때 아래 내용이 밀리지 않게 한다.
- 이유: 로딩 텍스트는 실제 내용과 높이가 달라서 끝나는 순간 화면이 튄다(CLS). 홈은 2026-10-10 개선으로 CLS가 0.13 → 0.001이 됐고, 다른 페이지도 같은 기준을 지킨다.
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 중복 제출 방지
- 상태: 확정
- 정책: 서버에 쓰기 요청을 보내는 버튼은 요청이 끝날 때까지 disabled로 둔다. 실패하면 다시 누를 수 있게 풀어준다. 서버 쪽 방어(주문 상태 `status` 조건 등, `CLAUDE.md`)와 별개로 화면에서도 막는다.
- 이유: 지금은 요청 중 비활성화가 `OrderTemplate`과 결제 버튼(유저 정보 로딩 중일 때만) 정도다. 리뷰 등록은 요청 중에도 다시 누를 수 있어서 같은 리뷰가 두 번 올라갈 수 있다.
- 코드: 잘 된 예 `src/widgets/OrderTemplate/OrderTemplate.tsx:186` / 없음 `src/features/review-write/ui/ReviewModal.tsx:152`, `src/features/qna/ui/Qna.tsx`, `src/features/order-manage/ui/Order.tsx`
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 결과 알림 방식
- 상태: 확정
- 정책:
  - 브라우저 기본 `alert()`/`confirm()`은 새로 쓰지 않는다. 확인이나 실패 안내는 `shared/ui` `AlertModal`(`useModal`)로 띄운다.
  - 성공은 화면 변화로 충분하면 알림을 띄우지 않는다 (장바구니 수량이 바뀌었으면 "변경되었습니다" 팝업 불필요). 화면에서 결과가 안 보이는 작업(리뷰 등록 후 이동 등)만 알린다.
  - 되돌릴 수 없는 작업(환불, 삭제)은 실행 전에 확인을 받는다.
- 이유: 지금 `alert()`가 38곳, `confirm()`이 2곳 있다. 사이트 디자인과 다르고, 뜨는 동안 페이지 전체가 멈춘다. `AlertModal`이 이미 `layout.tsx`에 있는데 거의 쓰이지 않는다.
- 코드: `src/shared/ui/AlertModal.tsx`, `alert(` 사용처 예 `src/features/review-write/ui/ReviewModal.tsx:187`, `src/app/(router)/manager/event/page.tsx:264`
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 에러 문구와 입력 보존
- 상태: 확정
- 정책:
  - 에러 문구에는 무엇이 안 됐는지와 사용자가 할 일을 쓴다 (예: "재고가 부족해 장바구니에서 삭제되었습니다", "잠시 후 다시 시도해주세요"). `오류가 발생했습니다`만 쓰지 않는다. 서버가 주는 `message`를 그대로 보여주되, 어떤 메시지를 내보낼지는 [에러 메시지 노출](./api.md)을 따른다.
  - 요청이 실패해도 사용자가 입력한 내용(리뷰 본문, 별점, QnA, 배송지)은 지우지 않는다.
- 이유: 지금은 실패 시 `오류가 발생했습니다.`만 보여주는 곳이 많아서, 사용자가 다시 시도할지 포기할지 판단할 수 없다.
- 코드: `src/features/review-write/ui/ReviewModal.tsx:195`, `:206`, `src/app/(router)/manager/product_add/page.tsx:317`, `:323`
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 낙관적 업데이트
- 상태: 확정
- 정책: 실패해도 손해가 없는 작업(좋아요, 장바구니 수량)은 서버 응답 전에 화면을 먼저 바꾸고, 실패하면 되돌리고 알린다. 돈·재고·주문 상태가 걸린 작업(결제, 환불, 배송 처리)은 반드시 서버 응답을 받은 뒤에 화면을 바꾼다.
- 이유: 기준이 없으면 결제처럼 실패할 수 있는 작업도 성공한 것처럼 보이게 만들기 쉽다.
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 빈 상태
- 상태: 확정
- 정책: 목록이 비어 있으면(장바구니, 주문 내역, 좋아요, 검색 결과, 리뷰) 빈 이유와 다음 행동을 같이 보여준다 (예: "장바구니가 비었습니다" + 상품 보러 가기 링크). 빈 화면이나 로딩 표시를 그대로 남기지 않는다.
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 성능 기준
- 상태: 확정
- 정책: 모바일 기준(p75)으로 LCP 2.5초 이하, CLS 0.1 이하, INP 200ms 이하를 목표로 한다(Core Web Vitals "좋음" 기준). 홈·상품 상세·장바구니를 크게 바꾸면 Lighthouse 모바일로 다시 측정해 이전 값과 비교한다.
- 측정: 지금은 Lighthouse로만 잰다. 실사용자 측정(Vercel Speed Insights)은 실제 트래픽이 생기면 켠다 (지금은 `@vercel/analytics`만 설치됨).
- 이유: 2026-10-10 운영 기준 홈 모바일은 Performance 80, LCP 3.6s(Lighthouse 제한 환경), CLS 0.001이다. LCP가 아직 목표보다 길다.
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정
