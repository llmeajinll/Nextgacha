## 재고 수정 방식
- 상태: 확정
- 정책: 관리자의 재고 수정은 "최종 수량 덮어쓰기"가 아니라 증감(`$inc`)으로 처리한다. 화면은 옵션별 증감량(+10, -2)을 보내고, 서버는 `arrayFilters`로 해당 옵션에만 `$inc`한다. 감소는 결과가 0 이상일 때만 적용한다(필터에 `count >= 감소량`). 가격 같은 재고 외 필드는 지금처럼 `$set`.
- 제외한 안: `updated_at` 낙관적 락. 주문 시 `reduceStock`은 `updated_at`을 바꾸지 않아서, 관리자가 화면을 연 뒤 들어온 주문을 잡지 못한다.
- 이유: 지금은 `list` 배열 전체를 `$set`한다. 관리자가 화면을 연 뒤 주문이 들어오면, 저장할 때 팔린 수량이 되살아나서 초과 판매가 생긴다.
- 코드: `src/app/api/postEditProduct/route.ts:26`, `src/features/purchase/lib/reduceStock.ts`
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정 (`$inc`)

## 관리자 입력값 검증
- 상태: 확정
- 정책: 관리자 API도 일반 API와 같은 수준으로 입력을 검증한다. 대상은 가격(양의 정수), 재고(0 이상 정수), 할인율, 택배사·송장번호(문자열·길이).
- 이유: 관리자 실수 한 번으로 결제 금액이나 재고가 깨진다.
- 코드: `src/app/api/postEditProduct/route.ts`, `src/app/api/postProduct/route.ts`, `src/app/api/postCheckToSending/route.ts:90`
- 변경 이력: 2026-11-09 신설, 2026-11-10 확정

## 관리자 작업 기록
- 상태: 확정
- 정책: 가격 변경, 재고 변경, 할인 변경, 환불, 송장 입력을 별도 컬렉션(`adminLogColl`)에 남긴다. 기록 내용은 누가(관리자 이메일), 언제, 무엇을(대상 상품·주문), 바꾸기 전·후 값. 5년 보존한다.

- 코드: 미구현. 대상 `src/app/api/postEditProduct/route.ts`, `postEvent`, `postCheckToSending`
- 변경 이력: 2026-11-09 신설, 2026-11-11 확정 (5가지 작업, 5년)
